# FORMAT — 交付物与输出格式

## 交付顺序

1. **完整 HTML 源码（作品本体）**：一个 standalone 单文件，建议文件名 `world-execute-me.html`；所有 CSS/JS/歌词/音频内联，不得省略任何代码；音频真实内联、播放可用、可调音量。最终大小不超过 30MB；过大时优先压缩对视觉表现无影响的部分。
2. **导演手记与方案比较（从简）**：读到什么；视觉主张；2 个或更多冲突方案与各自理由；选择/淘汰理由；主张与具体时间点、音乐段、歌词行的对应关系。每点 1–3 句即可，不追求篇幅。
3. **自检结果与边界交代**：按 [CHECKLIST.md](CHECKLIST.md) 逐项标注通过/不通过；按下文"边界交代"如实交代缺口。

## 完整性优先

- 若输出长度受限：**先保证 HTML 完整、可运行、效果不打折**；导演手记可压到最简（方案比较可压成要点），不得用"信息不足"替代判断。
- 若执行环境有文件读写/脚本能力：优先用脚本完成音频编码与 HTML 写入，交付 .html 文件本身，不要把数 MB base64 塞进对话。
- 若只能纯聊天输出、无法内联数 MB 音频：明确说明平台限制；不得用外链、假 base64 或"稍后自行填入"冒充完成——此时任务应判定为未完成，而不是交付一个不合规的成品。
- 无论何种方式，最终交付物必须是**一个**可保存并运行的 standalone HTML。

## 边界交代（信息不足清单）

用于交付时如实交代边界，**不是对判断的事前否决**：

> 数据没有的，你仍可基于听感和歌词做具体判断，只要标明是解读而非测量。把"信息不足"当成回避判断的理由，视为未达成创作目标。

默认写 3–5 句；只有下面确有缺失时才逐项写（没有缺失就不用凑条目）。每项写：缺什么 / 影响了什么判断 / 你如何处理：

1. 音频文件缺失、损坏、无法读取或无法内联；
2. 歌词原文未提供、行数与节奏表不符、或来源可疑；
3. 逐字/逐音素/逐音的演唱时刻与音高——数据只有行级时间窗与行级能量；你若基于听感讨论旋律/音高走向，标明是听感即可；
4. 起音（onset）事件列表——只有 `arrangement.onsetDensity`，单位未说明；
5. 人声/伴奏分离、和声、调性、和弦进行——数据未提供，但你可以按听感讨论（标明是听感/推断）；
6. `arrangement` 标签的生成方法、`section` 编号的语义；
7. 音频分析所用的窗长、归一化、频段划分、算法参数；
8. 官方 MV、创作背景、乐评、任何外部参考（本任务禁止引用）；
9. 音频版本/对齐信息；
10. 任何其他你试图使用但数据中没有的信息。
